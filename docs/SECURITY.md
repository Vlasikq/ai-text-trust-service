# Безопасность

Документ собирает модель угроз сервиса, принятые контрмеры и ограничения MVP. У каждого решения есть привязка к конкретному вектору атаки, а не общая ссылка на «best practice». Раздел «Известные ограничения» описывает места, где компромисс выбран сознательно: они помечены планом миграции в `ROADMAP.md`.

## Модель угроз

Сервис принимает русскоязычный текст пользователя и возвращает вероятностный вердикт «AI / human». Текст может быть чувствительным: студенческие работы, корпоративные документы, переписка. Поверхность атаки:

| Вектор | Угроза | Контрмера |
|---|---|---|
| HTTP `/api/v1/analyze` (без auth) | DoS объёмом, попытка раскрыть внутреннюю структуру | rate-limit, `max_chars`, скупые сообщения об ошибках |
| `/auth/login` | Brute-force, перебор email по timing/status | константное время + константное сообщение, slowapi 10/min |
| `/auth/register` | Массовая регистрация мусорных аккаунтов | slowapi 5/hour |
| `/auth/refresh` | Хищение refresh-токена (XSS, replay) | ротация + детект повторного использования, sha256 в БД |
| `/me/*` | Чтение чужой истории через подбор JWT | подпись HS256, проверка `status='active'`, фильтр по `user_id` в каждом репозитории |
| Batch CSV-загрузка | Раздувание ресурсов крупным файлом | `n_total > 0`, лимит размера в endpoint, partial-unique даёт один активный batch на пользователя |
| Логи | Утечка содержимого текста | `LOG_TEXT=false` по умолчанию, в БД только `sha256(text)` |
| Утечка деплоя | Подделка JWT после утечки секрета | отказ при старте, если `JWT_SECRET` остался дефолтным |
| Канал БД | SQL-injection | SQLAlchemy ORM с параметризацией, raw SQL c пользовательскими данными нет нигде |

## Аутентификация и сессии

### Хеширование паролей: argon2id

В [src/app/auth/passwords.py:18](src/app/auth/passwords.py#L18) используется `PasswordHasher()` из `argon2-cffi` с параметрами по умолчанию (memory_cost=65536 KiB, time_cost=3, parallelism=4). На современном CPU одна проверка занимает 50–100 мс. Почему argon2id, а не альтернативы:

- bcrypt обрезает пароли до 72 байт и не защищён от GPU-крекинга;
- scrypt менее распространён, библиотек меньше, поддержка хуже;
- argon2id выиграл Password Hashing Competition 2015 и единственный имеет защиту от side-channel и time-memory trade-off. OWASP рекомендует его как первый выбор с 2021 года.

Параметры — компромисс. Слабее — защита снижается, сильнее — `/auth/login` сам становится DoS-вектором за счёт нагрузки на CPU.

### Логин с постоянным временем

В [src/app/auth/passwords.py:24](src/app/auth/passwords.py#L24) `_DUMMY_HASH` считается один раз при импорте модуля. Если по email пользователя нет, `/auth/login` всё равно вызывает `burn_dummy_verify_async(password)`: argon2 прогревает тот же CPU, что и реальная проверка пароля. Так закрывается таймингный канал, по которому злоумышленник мог бы перебирать зарегистрированные email.

Без этой меры на «известный email + неверный пароль» уходит ~75 мс (вызов `argon2.verify`), а на «неизвестный email» меньше миллисекунды, потому что хешировать нечего. По латентности ответа можно было бы построить перечень зарегистрированных адресов, даже не угадывая пароли. Холостой verify выравнивает обе ветки.

### Одинаковые ответы на ошибки авторизации

`/auth/login` и `/auth/refresh` возвращают `401 Invalid email or password` и `401 Invalid or expired refresh token` независимо от того, что именно пошло не так: нет пользователя, неверный пароль, протух токен или его отозвали. Этим закрывается утечка статуса: клиент не может различить ситуации «такого email нет» и «пароль неверный».

### JWT access-токены: HS256

В [src/app/auth/tokens.py:33](src/app/auth/tokens.py#L33) функция `create_access_token` собирает токен с такими claim'ами:

```json
{"sub": "<user_id>", "role": "user|admin", "iat": ..., "exp": ..., "type": "access"}
```

Время жизни — 15 минут (`access_token_ttl_minutes`). Декодирование stateless: `decode_access_token` не обращается к БД, только проверяет подпись и срок. За счёт этого API масштабируется горизонтально без общего хранилища сессий.

Симметричный HS256 выбран вместо асимметричных RS256/ES256 по трём причинам. API одновременно подписывает и проверяет токены, поэтому не нужно публиковать public key. JWKS-эндпоинта нет, и не приходится ротовать пары ключей. Один секрет — одна точка хранения, что упрощает аудит.

Цена решения: при утечке `JWT_SECRET` злоумышленник сможет подделать любой токен. Митигация — `_validate_settings_for_prod` в [src/app/main.py:115](src/app/main.py#L115), который падает с `RuntimeError`, если `IS_PRODUCTION=true`, а секрет остался дефолтным. Так отсекается распространённая ошибка «забыл переопределить через ENV». Хранение самого секрета обсуждается ниже в разделе «Известные ограничения».

### Refresh-токены: непрозрачные, с ротацией и детектом повтора

В [src/app/auth/tokens.py:81](src/app/auth/tokens.py#L81):

```python
def create_refresh_token() -> str:
    return secrets.token_urlsafe(32)  # 256 бит криптографической энтропии

def hash_refresh_token(token: str) -> str:
    return hashlib.sha256(token.encode("utf-8")).hexdigest()
```

В БД лежит только `sha256(token)` в поле `refresh_tokens.token_hash`. Сам токен клиент видит ровно один раз — в ответе на login, register или refresh.

Ротация описана в [src/app/routers/auth.py:208](src/app/routers/auth.py#L208) и работает так:

1. Клиент посылает `POST /auth/refresh` с текущим refresh-токеном.
2. Сервер находит запись по `sha256(token)`, проверяет, что `revoked=false` и `expires_at>now()`.
3. Создаёт новую пару access + refresh.
4. Прежний refresh помечает `revoked=true`, поле `replaced_by_id` указывает на новый.
5. Отдаёт новую пару клиенту.

После этого старый refresh уже не примут. Окно эксплуатации украденного токена ограничено временем до следующего обращения легитимного пользователя.

Детект повторного использования — [src/app/routers/auth.py:232](src/app/routers/auth.py#L232):

```python
if existing.revoked:
    await uow.refresh_tokens.revoke_all_for_user(existing.user_id)
    log.warning("refresh token reuse detected")
    raise invalid
```

Сценарий: злоумышленник украл refresh, обменял его на новую пару, а спустя время легитимный пользователь приходит со своим старым refresh — и наталкивается на `revoked=true`. Значит, токеном уже воспользовались. В этот момент сервер отзывает всю активную цепочку refresh-токенов этого пользователя и заставляет залогиниться заново. Доступ атакующего обрывается при первой же активности жертвы.

### Logout

`POST /auth/logout` идемпотентен: повторный вызов с уже отозванным токеном вернёт 204 без ошибок. Access-токен здесь не требуется, и разлогиниться можно даже когда access уже протух. Это нужно PWA: пользователь жмёт «выйти» на странице, где access уже невалиден.

## Защита от перебора и DoS

Rate-limiting сделан через [slowapi](https://slowapi.readthedocs.io/) в [src/app/middleware/ratelimit.py](src/app/middleware/ratelimit.py). Функция-ключ `_key_func` делит трафик на два бакета:

- `auth:<token-prefix>` для запросов с `Authorization: Bearer ...`; в ключ идут первые 32 символа JWT;
- `ip:<x>` в остальных случаях; адрес берётся с учётом `X-Forwarded-For`, потому что сервис стоит за Caddy.

Лимиты задаются в `Settings` и переопределяются через ENV:

| Endpoint | Лимит | За что отвечает |
|---|---|---|
| `/api/v1/analyze` | 60/min | основной endpoint, обычный темп UI |
| `/api/v1/jobs` | 20/min | async-режим: запросов меньше, обработка медленнее |
| `/api/v1/batch` | 5/hour | CSV-загрузка до 100 текстов за раз |
| `/api/v1/extract/text` | 30/min | предпросмотр при drag-and-drop |
| `/me` и `/me/*` | 60/min | страница «личный кабинет» |
| `/auth/login` | 10/min | защита от brute-force |
| `/auth/register` | 5/hour | защита от массовой регистрации |
| `/auth/refresh` | 60/min | UI рефрешит часто |
| `/auth/logout` | 10/min | защита от мусорных вызовов |

Хранилище счётчиков — in-memory в пределах процесса. Ограничение сознательное, обсуждается ниже в «Известных ограничениях».

Чего лимиты не закрывают: распределённой атаки с большого пула IP. Для этого нужны правила WAF на уровне Caddy или внешнего балансировщика — отнесено к плану после защиты.

## Приватность по умолчанию

### Текст не сохраняется в БД

В таблице `analyses` лежат:

- `text_hash` — `sha256(cleaned_text)`, нужен для дедупликации в analytics и для кэша;
- `text_length` — для статистики, не для восстановления;
- результат детекции: `verdict`, `confidence`, `risk_level`, `warnings`.

Чего там нет: сырого текста, токенизированных представлений, эмбеддингов, шинглов. Если БД скомпрометируют, восстановить содержимое анализов из неё нельзя.

### `analysis_jobs.input_text` зануляется

Async-задачи — единственное место, где текст временно хранится в БД, потому что воркер должен его забрать. По завершении (`mark_success` или `mark_error`) поле явно зануляется. См. [src/app/database/models.py:174-177](src/app/database/models.py#L174-L177) и методы `JobRepository.mark_*`.

### `LOG_TEXT=false` по умолчанию

Флаг `Settings.log_text` ([src/app/config.py:63](src/app/config.py#L63)) предназначен для отладки. В проде остаётся `false`: middleware и обработчики не пишут текст в structured-логи. В Loki и Cloud Logging содержимого тоже не появляется.

### CORS со строгим allow-list

В [src/app/main.py:226](src/app/main.py#L226) `CORSMiddleware` подключается только если `CORS_ORIGINS` непустой. Разрешённые методы — `GET, POST, OPTIONS`. Разрешённые заголовки — `Authorization`, `Content-Type`, `X-Correlation-ID`, `X-Request-ID`. `allow_credentials=True` оставлен на будущий переход к BFF и httpOnly-куки. В текущем same-origin-сетапе (PWA и API на одном домене) `CORS_ORIGINS=""`, и браузер кросс-доменно ничего не запрашивает.

### Версионирование

Значение `SERVICE_VERSION` должно совпадать в трёх местах: `pyproject.toml`, `Settings.service_version`, тег docker-образа. Если, например, поправили только `pyproject.toml`, но забыли про `env` в `docker-compose.prod.yml`, Swagger UI и поле `Analysis.service_version` будут показывать старую версию, а образ — новую. На код-ревью это легко пропустить. Чтобы такого не было, источник правды на стороне деплоя один: `SERVICE_VERSION` задаётся в env-блоке docker-compose и оттуда подтягивается в `Settings`.

### Резервный канал записи при падении БД

Если PostgreSQL упадёт во время работы, `persist_analysis_with_fallback` из [src/app/database/persist.py](src/app/database/persist.py) запишет результат анализа в JSONL-файл по пути `DB_FALLBACK_LOG_PATH`. Сервис продолжит отвечать клиентам, и деградация останется частичной. Так появляется окно в несколько часов на восстановление БД без общего простоя.

## Управление секретами в репозитории

`scripts/deploy/docker-compose.prod.yml`, `*.rendered.*` и `*.local.*` помечены в `.gitignore` как чувствительные: они содержат продовый `DATABASE_URL` и `JWT_SECRET`. Дев-вариант `scripts/deploy/docker-compose.yml` и шаблон `cloud-init.yaml.template` (без подставленных значений) остаются под версионным контролем, потому что в них нет реальных секретов.

Правило простое: если файл получает значение из `render_cloud_init.py` или `render_compose_prod.py`, он не коммитится. Перед `git add scripts/deploy/` стоит проверить `git status --short scripts/deploy/` и `git check-ignore -v scripts/deploy/docker-compose.prod.yml` — для prod-варианта должен вернуться путь и номер строки `.gitignore`.

Если по неосторожности секрет всё-таки попал в коммит — рассматривать его как скомпрометированный: повернуть `JWT_SECRET` через `openssl rand -hex 32`, в YC Managed PostgreSQL выпустить новый пароль для пользователя `aitrust`, перевыпустить `docker-compose.prod.yml` через рендерер. Чистка истории (`git filter-repo` или BFG) — отдельный шаг, который сам по себе не отменяет утечку, потому что зеркала и GitHub-кэши уже могут содержать старую ревизию.

## Известные ограничения (для MVP)

Все пункты ниже — компромиссы, выбранные сознательно. Для каждого есть план миграции в `ROADMAP.md`.

### 1. Refresh-токен лежит в `localStorage`

В [apps/web/src/lib/api.ts:12](apps/web/src/lib/api.ts#L12) refresh-токен хранится в `localStorage`. Доступ к нему есть у любого JavaScript на странице, и при XSS-инъекции токен можно унести.

Почему так в MVP: альтернатива — BFF c httpOnly и SameSite=Strict-куки. Поскольку Caddy уже даёт same-origin, отдельный BFF необязателен, можно расширить `/auth/refresh` на чтение токена из куки. Это перепишет фронт и один endpoint, поэтому отложили.

Митигация на сегодня: Content-Security-Policy в Next.js жёстко ограничивает источники скриптов, а детект повторного использования refresh-токена (см. выше) сужает окно для злоумышленника.

### 2. `JWT_SECRET` в открытом виде в docker-compose

В [scripts/deploy/docker-compose.prod.yml:25](scripts/deploy/docker-compose.prod.yml#L25) секрет хранится в открытом виде. На YC-виртуалке файл лежит в `/opt/aitrust/` с правами `0644`.

Почему так в MVP: YC Lockbox требует sidecar или вызова API при старте плюс отдельной настройки IAM. Усложнение деплоя оправдано, только если оно реально что-то закрывает. Угроза для secrets в файле возникает при компрометации root-доступа к виртуалке, а в этом случае и без секретов всё потеряно.

Митигация на сегодня: публичного SSH у виртуалки в проде нет. Debug-ключ, прописанный в cloud-init, убирается после защиты ВКР (см. комментарий в `scripts/deploy/cloud-init.yaml.template:7`).

### 3. Закрыто: миграция с python-jose на pyjwt

В [src/app/auth/tokens.py:13](src/app/auth/tokens.py#L13) — `import jwt; from jwt.exceptions import InvalidTokenError`. До мая 2026 здесь была `python-jose`. Библиотека получила CVE-2024-33663 (algorithm confusion) и CVE-2024-33664 (jwks DoS), последний релиз вышел в 2022 году. Заменили на `pyjwt`, которая активно поддерживается.

API почти такой же: `jwt.encode(payload, key, algorithm="HS256")` и `jwt.decode(token, key, algorithms=[algorithm])`. Все ошибки декодирования (просрочка, неверная подпись, повреждённый токен) наследуются от `InvalidTokenError`, и в `decode_access_token` мы ловим базовый класс, нормализуя его в собственный `TokenError`.

### 4. Rate-limit считается в памяти процесса

В [src/app/middleware/ratelimit.py:42](src/app/middleware/ratelimit.py#L42) — `Limiter(key_func=_key_func, default_limits=[])` без `storage_uri`. Последствия:

- при одном воркере лимиты работают как заявлено;
- при горизонтальном масштабировании каждый процесс считает счётчики у себя, и фактический предел становится равен `N_воркеров × значение из конфига`.

Почему так в MVP: один контейнер с одним процессом, и в этой конфигурации лимиты корректны. Общий Redis добавил бы в стек ещё один сервис — отдельный контейнер, healthcheck, бэкапы.

План: когда появится больше одного процесса API, перенастроить slowapi на `storage_uri="redis://..."`.

### 5. Контейнер `artifact-sync` работает от root

В [scripts/deploy/docker-compose.prod.yml:71](scripts/deploy/docker-compose.prod.yml#L71) задан `user: "0:0"`. Named volume по умолчанию принадлежит `root:root`, и `appuser` с uid 1000 не может создавать в нём папки. Контейнер `artifact-sync` поднимается, копирует трансформер (~1.4 ГБ) с правами `0644`, и завершается. API и воркер потом читают файлы по правилам для группы `other`.

Почему так в MVP: альтернативы — init-контейнер, который один раз меняет владельца тома, или сборка кастомного образа с нужными uid. Текущее решение проще и работает; контейнер живёт не больше минуты.

Митигация: у `artifact-sync` нет открытых портов, входящих соединений и shell. Это разовый скрипт.

### 6. Container Registry открыт на чтение

В YC CR навешан `system:allUsers / images.puller`, и любой может скачать образы `aitrust-api:0.3.X` и `aitrust-web:0.X`.

Почему так в MVP: альтернатива — IAM-токены на pull, которые усложнили бы cloud-init. Сервис задумывался как стенд для защиты ВКР, и коммерческой тайны в коде нет.

Что при этом не утекает: секреты (они лежат в ENV, а не в образе) и пароли от production-БД.

### 7. Одна виртуальная машина, без HA

Прод-стенд — одна Compute Instance в YC. PostgreSQL поднят как Managed, и у него HA из коробки. У API и фронта такой защиты нет, и они остаются единичной точкой отказа.

Почему так в MVP: это стенд для ВКР, а не сервис с SLA. HA потребует второй виртуалки, Application Load Balancer, общего хранилища сессий (Redis) и синхронизации артефактов между машинами.

План: рассмотреть после защиты, если сервис продолжит жить.

### 8. Async-режим в PWA пока не подключён

Фронт ([apps/web/src/components/AnalyzeForm.tsx](apps/web/src/components/AnalyzeForm.tsx)) ходит синхронно в `POST /api/v1/analyze`. Для каскада в «серой зоне» на CPU ответ может занять 5–15 секунд.

Почему так в MVP: дефолтный детектор в проде — `cascade`, но 92% запросов резолвятся быстрым TF-IDF меньше чем за 100 мс. Серая зона редкая, и синхронный путь приемлем. Поллинг `/api/v1/jobs/{id}` в UI — задача после защиты.

| Решение | Альтернатива | Почему не выбрали |
|---|---|---|
| OAuth/OIDC через стороннего провайдера | Свой JWT и argon2 | Один пользователь — один аккаунт, SSO не требуется. Сторонний провайдер добавил бы зависимость и сетевой переход на каждый логин. |
| Шифрование текста в БД | Только `sha256` | Восстанавливать тексты нам не нужно. Шифрование с возможностью расшифровки превращает БД в основную мишень. |
| Куки вместо Bearer | Bearer для API, refresh в `localStorage` | API должен оставаться вызываемым из Telegram-бота, скриптов и `curl`. Bearer покрывает все эти сценарии. |
| Captcha на login/register | Только rate-limit | Бот-ферма против русскоязычного академического сервиса на стадии MVP маловероятна. Captcha добавила бы сторонний сервис в критический путь логина. |
| 2FA | Только пароль | Объём MVP. Сервис академический, не финансовый. |
